# 京都の全収録範囲を表示する地図

追記: この文書は初版の記録。広域の集計セルは、その後[建物外形の簡略表示](2026-10-26-kyoto-footprint-overview.md)へ置換済み。最新の表示方式・測定結果はそちらを参照。

利用者指示: 京都PLATEAU全収録範囲の全壊率を高速表示し、エミュレーター実験後にvivo実機測定を行う。先の軽量化・先読み・縮尺別描画の提案を踏まえ、実装の指示を受領済み。

実装判断: 既存MapLibreを維持。事前生成したMVTをAPK assetsから直接読み、外部サービスを追加しない。GeoJSON全件の端末解析は避ける。低ズーム8〜13はセル内評価可能建物の平均全壊率（棟数・不明数も保持）、14以上は元外形をタイル境界で切り出した建物ポリゴン。元データのIDと被害曲線分類を保持し、震度変更は描画式を更新して対応。数値・色・タップ時詳細は共通モデルを用いる。既存の色とシートを利用し、意味に必要な文言のみ調整。

初期震度: 利用者が計測震度6.2を承認済み。実機接続による測定も承認済み。

工程:
1. タイル生成の境界・穴・全件集計をテストしてから生成。
2. 地図にタイルソース・評価描画・詳細を組み込む。
3. JVMと端末テストで、原曲線との一致、描画、タップ、震度変更を確認。
4. エミュレーターで初回・連続移動・広域表示・メモリを測定し、改善。
5. 実機で同じ条件を測定。接続されない場合は未実施を明示する。

速度は実測値で報告し、Googleマップとの同等性は比較実測なしに断定しない。別チャットが編集するdemoディレクトリは触らない。


## 先行検証

- Python: タイル境界・内周・不明を除いた平均・空タイルの4テストが成功。
- JVM: 建物評価5テスト、表示モデル3テストが成功。
- エミュレーター: API37 / Google SwiftShader。初回の先行試験は消灯状態で地図の初期化待ちが失敗。画面点灯後の再試験で描画を確認（252個の描画中フィーチャー）。この先行試験は詳細度14のタイルのみで、最終性能測定には使わない。
- GitHubのMapLibre Native実装で先読み設定も確認。今回の先読みは縮尺の粗い親タイルの取得であり、移動方向を予測する独自の周辺先読みではない。
- 生成結果の全2,329タイルのハッシュを確認。最高詳細度タイルを復号し、元の513,815建物IDと曲線分類を全件照合して一致（欠落0）。広域集計も513,815棟で一致。記録は `data/2026-10-26-kyoto-map-integrity.json`。

## 最終版の検証記録

- 初期震度6.2。低10%未満、中10%以上40%未満、高40%以上。
- 建物データはAPK内から取得。背景地図のOpenFreeMap取得・既存オフライン保存の仕組みは従来どおりで、背景地図全体を通信不要にした変更ではない。
- MVT本体138,503,587 bytes、メタデータを含むAPK内圧縮サイズ79,863,166 bytes。最終debug APK全体221,484,693 bytes（約221 MB）。高速表示のための事前生成データを同梱する容量上のトレードオフがある。
- Pythonの4テストと建物関連JVMの8テスト成功。Android debug本体・端末テストAPKのビルド成功。
- エミュレーターの `BuildingRiskMapTest` 成功。建物表示、広域集計表示、描画式の震度変更、実際の建物タップによる数値の一致、凡例への遷移を確認。
- エミュレーターはAPI37・SwiftShaderによるソフトウェア描画。PC空きメモリ約0.7 GBの状態で、全壊率非表示でも大きな遅延があった。起動中の既存WorkManager初期化でも一度ANRを記録。最終の地図操作試験は成功したが、性能値を実機の期待値として使わない。
- エミュレーター計測: 初回表示14,410 ms、広域表示2,252 ms、PSS 317,231 KiB。生データは `data/2026-10-26-kyoto-map-emulator.json`。初回時間はActivity作成から建物の描画確認までで、背景スタイルの取得も含む。全タイルの描画完了時間ではない。
- vivoではComposeテストの起動が待機し続け、直接の `startActivitySync` も45秒で起動待ちに失敗した。通常のMainActivityはUSBから起動できたため、debug限定・DUMP権限で保護した測定ActivityをUSBから直接起動する検証経路を用意した。端末の起動制限設定は変更していない。
- MapLibreの描画完了コールバック間隔は画面の厳密なFPSやAndroid FrameMetricsとは異なる。Googleマップとの直接比較でもない。

## vivo実測（V2417A / Android API36）

`BuildingRiskDeviceTest` はUSBから測定Activityを直接起動する方式で成功。通常版と同じSituationScreen、MapLibre、全収録タイルを使用。住民・災害レコードは変更しない。

最初の成功測定（`data/2026-10-26-kyoto-map-vivo.json`）:

| 指標 | 測定値 |
|---|---:|
| Activity作成から建物が現れるまで | 494 ms |
| 広域の地域平均が現れるまで | 73 ms |
| 1秒指定の移動完了＋表示確認・全壊率なし（5区間中央値） | 1,013 ms |
| 同・全壊率あり1周目 | 1,091 ms |
| 同・全壊率あり2周目 | 1,090 ms |
| 描画コールバック間隔 p50・なし | 17.20 ms |
| 同・あり1周目 / 2周目 | 17.34 / 17.71 ms |
| 描画コールバック間隔 p95・なし | 24.18 ms |
| 同・あり1周目 / 2周目 | 21.37 / 21.65 ms |
| 取得フレーム間隔数・なし / あり1周目 / 2周目 | 275 / 290 / 287 |
| 試験終盤のアプリPSS | 622,619 KiB（約608 MiB） |

この経路・端末・debug版では、全壊率描画による追加の描画間隔は小さい。背景地図と端末キャッシュを消去していないため、初回値は完全な未キャッシュ起動やインストール直後全体の起動時間ではない。初回・広域値はいずれも最初のフィーチャーの出現であり、全背景タイルの取得完了を意味しない。PSSは試験プロセス全体の値で、建物レイヤー単独の使用量ではない。

エミュレーターとvivoで測定ハーネスが異なるため、両者の数値を厳密な端末性能比較として扱わない。vivo内の有無比較は同じ測定ハーネス・経路を使用。なしを先に実行し、後半ほどキャッシュが温まる順序の影響も残る。

収録範囲表示ボタンは固定ズームから、513,815棟の収録範囲と画面縦横比に合わせた表示へ変更。最終再測定で両隅が画面内に含まれることを検証して成功。最終版はvivoにインストール済みで、試験終了後に通常のMainActivityを起動した。端末の再起動は行っていない。

最終再測定（`data/2026-10-26-kyoto-map-vivo-final.json`）も成功。建物表示270 ms、広域表示67 ms。描画間隔p50はなし17.15 ms、あり17.72 / 17.77 ms。p95はなし25.95 ms、あり21.40 / 21.91 ms。PSSは813,109 KiB（約794 MiB）で、初回測定より増加している。この測定だけで長時間利用時のメモリ安定性を保証しない。主目的の地図移動は2周とも同程度だった。

利用者から「広域にすると広い範囲が色づく理由」の質問を受領。現在の低ズームは平均値の区画全面塗りで、道路・空き地まで着色する。土地の危険度ではない。これは高速化の唯一の方式ではなく、建物外形を簡略化して表示する代案がある。質問時点で広域表示方式を勝手に変更せず、見え方と意味を説明した。
