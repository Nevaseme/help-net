# Tasukeai：追加機能の実装計画

> **For agentic workers:** Use executing-plans or subagent-driven-development for the confirmed implementation units below. Unconfirmed product choices are not authorization to invent specifications.

**Goal:** add.txtの追記9項目を既存工程へ接続し、iOS PWA・複数Androidの共用基盤を最優先で整える。

**Architecture:** 端末内保存と既存記録ID・訂正規則を維持し、無料クラウドの永続保存と再接続同期を追加する。地理データ、津波計算、職員派遣、地域レポートは独立した機能として同じ記録・配信基盤へ接続する。

**Tech Stack:** 既存Kotlin／Compose／Room／MapLibre、JavaScript PWA／IndexedDB、Cloudflare、Firebase FCM。津波計算アダプターはANUGA3.3.10。

**Spec:** [追加設計](../specs/2026-10-30-additions-design.md)

## 共通条件

- 無料必須、通常利用はこのPCの起動に依存しない。外部サービス追加を最小にする。
- plan.txtとadd.txtを編集しない。京都の建物評価6.2、区分10%／40%を変更しない。
- 実装と検証は別に記録し、iOS実機未確認をAndroid・ブラウザー試験で代替済みとしない。
- 新しい画面を実装した場合は既存のWeb反映ルールを守る。別チャットの公開デモ変更を上書きしない。
- B1〜B9は今回の追記のID。A1〜A6の採用や終了条件は取り消さない。B9のみ採否待ちの任意候補。

## 優先順と依存

**直近の優先：B8 → 複数端末の通し試験。** B4の計算方式・候補地域・独立ベンチマークの作業は並行する。B1＋B6、B2＋B3、B7はB8の試験待ちに独立して進められる。B5は参加者・役割・位置・通知を使うためB8とA3に依存する。B9はB7の確定集計が動いた後に採否を決める。

従来の「通信の実機結合試験は後半」は、今回の優先指示によりB8の実証について先に行う。追加Android／iPhoneがない試験は未実施と残し、そのために保存・サーバー・計算の開発を止めない。

## 実装単位と検証

### 1. B8：保存・接続経路と参加者

既存箇所：`lab/router.mjs`、`lab/server.mjs`、`lab/web/sync.mjs`・`managed-store.mjs`・`managed-records.mjs`、Androidの`core/SyncEngine.kt`・`data/QuakeStore.kt`・`lab/LabController.kt`、`eew-relay/`。新しいクラウド同期処理は実験A/B/Cと区別して配置する。

- [x] 現在のA固定・1役1台・非保存・名簿更新不可を再現し、共有基盤の具体設計を保存する。
- [x] 管理者による作成、参加、端末の識別、名簿の更新と権限を実装し、別グループ・未参加・一般メンバーの管理操作を試験する。
- [x] 永続保存と同期APIを実装し、通信切断、再送、重複、順不同、同一ID競合、保存失敗時ACKなしを試験する。
- [x] HTTPSのPWA配信とAndroid接続を実装する。証明書の手動導入やPCローカルURLを不要にする。
- [ ] 先行端末が切断してから後続端末を接続し、サーバー保存済みの記録・訂正・管理者終了を取得できることを確認する。
- [ ] iOS PWAと2台のAndroidで実施。端末不足・iOS背景制約・無料枠の限界を分けて記録し、サーバーへの到達と相手端末の保存を区別する。

### 2. B1＋B6：建物・住所・住民対応

既存箇所：`tools/building_analysis/`、Android `buildings/`・`core/PlaceEvent.kt`、`lab/web/places.mjs`・`place-ui.mjs`。

- [ ] 住所情報の候補データを京都の小範囲で照合し、複数棟・住所欠損・代表点と輪郭のずれを報告する。
- [ ] 建物IDと住所の対応・候補検索・選択訂正を実装する。PLATEAU版の変更時に既存住民の関連付けを消さない。
- [ ] 架空住民の割当てを固定入力で再現し、建物→住民と住民→建物の件数・IDを照合する。

### 3. B2＋B3：標高・地盤

- [ ] 採用するデータの範囲・版・解像度・座標基準を小範囲で確認する。
- [ ] 区画ごとの配布・読込・地点照会を実装し、欠損・境界・0m・基準不一致を試験する。
- [ ] 地図上の表示は選択した指標と一致させる。オフラインと再読込を試験する。

### 4. B4：津波の計算・配信・表示

- [x] PLATEAUの整備状況と標高差を根拠に熱海・沼津を比較し、利用者が熱海市中心部を選択した。
- [x] 陸上DEMと海底地形、波形、潮位、粗度、時間・格子条件を記載したシナリオ形式を定義する。欠損入力を推測値で埋めて実地域計算を始めない。`tools/tsunami/README.md`とシナリオ検証を参照。
- [ ] 動的な浸水／退水を扱う計算エンジンを用意し、静水、質量収支、乾湿境界、解析解・公開実験、刻み幅の収束を試験する。
- [ ] 無料・PC非依存の運用に合う計算場所を検証する。事前計算の配信方式を使う場合は選択できる津波条件を明示し、未計算条件を計算済みとして表示しない。
- [ ] 実地域の計算を実行し、計算条件・使用データ・結果IDを保存する。公表想定との比較は前提条件の違いを記録する。
- [x] Android/PWAで同じ固定結果を読み、最大浸水深を地図表示する。両方の10m/20m切替・圏外表示を検証する。
- [ ] 時刻別浸水のアニメーションと、追加の波高条件を計算・選択できるようにする。

2026-10-30追補：熱海沿岸780×580mの目標海岸高3mを20m/10mで実計算し、固定結果と出典・監査図を保存した。両方とも同じ境界種類と波形時間、各格子で海岸目標高へ個別校正。陸上1cm以上の面積19,300/22,400m²、最大深3.353736/4.388558mで差が残る。同一沖側振幅による厳密な収束試験や実測値検証は未完了。PWA1.5.2公開版とAndroid1.5.17エミュレーターに最大浸水深表示を実装・検証した。住居登録・災害開始に依存せず地図閲覧可能。任意高さと時刻別表示は未完了。

### 5. B5：避難所確認

- [ ] 距離の定義、職員の対象条件、位置の鮮度、起動条件、再割当て権限を確定する。
- [ ] 候補選定→通知→受諾／辞退→到着→状況報告を、架空の職員・避難所で実装・保存する。
- [ ] 同距離、位置不明、対応中、受信不能、二重通知、担当交代、確認結果の訂正を試験する。

### 6. B7と任意候補B9：地域報告

既存箇所：Android `core/RegionalSummary.kt`・`OperationsExport.kt`、`lab/web/regions.mjs`・`operations-export.mjs`。

- [ ] 対象災害・地域・期間・分類と出力書式を決める。
- [ ] 同一案件の重複を除き、町内会・区の定型レポートと根拠明細を生成する。発行版を保存し、訂正後の再発行と照合する。
- [ ] B9は採用された場合だけ別実装する。AIなしの集計を基準に誤要約・根拠欠落・無料枠到達を検証する。

## 重点確認

1. B8：複数端末参加後の名簿更新を拒否しないか。既存住民・管理者権限を保持する。
2. B1/B6：住所候補だけで別棟に住民を確定しないか。割当ての訂正が全表示へ反映される。
3. B4：海岸津波高・水位・陸上浸水深と標高基準を混同しないか。乾燥セルで負の水深や数値発散が起きない。
4. B5：近いという理由だけで位置不明・活動不能の職員に対応済みを付けないか。通知と実際の確認を分ける。
5. B7/B9：要約で通報・訂正・未確認情報が消えないか。元記録と発行時点を追跡できる。

各単位の詳細なAPIとファイル追加は着手時に固定する。本書の未確定事項を実装者の好みで決定済みと扱わない。今回の文書反映は、追加機能が動作したことの報告ではない。
