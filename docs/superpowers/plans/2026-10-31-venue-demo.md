# 会場デモ Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 聴衆がQRから参加し、安否回答と通報を地図で共有し、Androidではインターネットなしの保存・中継、PWAでは通信復帰後の自動同期を体験できる会場デモを作る。

**Architecture:** 既存のCloudflare共有サーバー、AndroidのRoom／Nearby／SyncEngine、PWAのIndexedDB／Service Workerを使う。会場デモの設定と架空座標はグループ・実施回に紐付けて配布し、既存の実際の位置記録とは別に保持する。近距離で受け取った情報も保存し、別の端末に後から運ぶstore and forwardを維持する。

**Tech Stack:** Kotlin／Compose／Room／Google Nearby Connections、JavaScript PWA／IndexedDB、Cloudflare Workers／Durable Objects SQLite。

**Spec:** 本文「1. 利用者が指定したシーン」。2026-10-31の利用者指示を保存。これは計画であり、下記の未実装機能が既に動いているという報告ではない。

## Global Constraints

- 聴衆は**合計最大40人程度**。そのうちAndroidは0〜20人程度。PWA人数は残りであり、「Android20＋PWA40＝聴衆60人」ではない。従来の60記録試験は余裕を持った負荷試験の履歴として残す。
- 運営・管理者の端末は聴衆と分けて数える。必要台数を決めてから、試験人口へ追加する。
- 無料の既存サービスを使い、このPCの常時稼働に依存しない。
- グループは管理者が作成し、聴衆はスライド上のグループ名・参加パスワードで一般メンバーとして参加する。
- 名前登録後は安否画面、無事／SOSの保存後は地図へ進む。会場デモ中は住所・住居の追加入力を要求しない。
- 会場デモモードのみ、利用者が確定した御所南〜烏丸御池周辺へ架空の位置を分散する。避難訓練モード・地震モードは実際の位置情報を使う。
- 地図／一覧／対応／安否の既存配置を土台にし、初回案内とモードに必要な変更だけを接続する。画面変更時は既存ルールどおり比較ページと公開Webへ反映する。
- `plan.txt`、`add.txt`、既存の登録・実験記録を変更・削除しない。参加パスワード、秘密鍵、APK、実機DBをGitに追加しない。

## Review Focus

1. 管理者の開始より後に加入した人が、既に始まっている同じ実施回へ回答・通報できるか（Task 1、3）。
2. 先に参加した端末が古い名簿しか持たず、後から参加した人のオフライン記録を拒否しないか（Task 3、4）。
3. 実GPSによって架空配置が上書きされたり、訓練・本番で架空配置が残ったりしないか（Task 2）。
4. サーバー応答が失われて再送しても、加入・安否・通報が重複しないか。通信復帰時に別のグループを同期しないか（Task 1、5）。
5. オフラインで初めて地図を開く・移動する・再起動する際、地図資材不足や保存失敗でデモが止まらないか（Task 3、6）。

## 1. 利用者が指定したシーン

1. 発表者がスライドにQRを表示。Android利用者はAPKをインストールし、iOS利用者はPWAをホーム画面へ追加する。
2. 発表者は事前に管理者として会場デモ用の地震シナリオを開始している。
3. 聴衆がスライドのグループ名・パスワードを入力して参加し、自分の名前を登録する。
4. 自動で安否登録画面へ進み、「無事」または「SOS」を選ぶ。
5. 回答保存後は地図へ進む。既に回答した参加者と自分が地図に表示され、後から参加した人も追加される。会場デモの初期表示では無事・SOSの両方を表示する。
6. 全員の参加・初回同期・オフライン用の準備が済んだ後、インターネットを切る。
7. Android同士は安否変更や通報の追加・更新を近距離で交換し、自分と相手の地図に反映する。一時的な切断では端末内に保存し、後の接触で中継する。
8. PWAは切断中も自分の操作を保存するが、他端末との圏外交換は行わない。ネット復帰後、PWAの再送ボタンを押さずに送受信し、画面を更新する。
9. 会場の同一地点に参加者が重ならないよう、指定地域へ架空位置を分散する。実際の避難訓練・地震では実位置に切り替わる。

このシーンの中心は「回答・通報がネットなしでも別端末へ届く」こと。前回候補のリアルタイム在席確認だけを先行する計画から、本シーンに合わせた参加→回答→地図→切断→再同期へ優先順位を変更する。最終更新時刻は表示できるようにするが、保存記録だけで現在そこに人がいると断定しない。

### 2.1 Androidのインターネット遮断

NearbyはBluetooth／BLE／Wi-Fiを利用するオフラインP2Pであり、インターネット自体は不要。[Google公式概要](https://developers.google.com/nearby/connections/overview)

一方、「Wi-Fi完全OFFのままで全てのAndroidが同じように動く」は別の条件である。実機1.5.22試験でも、vivoはWi-Fi OFF、XiaomiはWi-Fi ON・AP未接続でネット経路なしだった。これを両方のWi-Fi完全OFF成功と記載しない。

Googleは2026年後半にNearbyによる無線自動ONの動作変更を予定しており、利用者による必要な無線の有効化を求めている。旧端末で自動ONになった実績に依存しない。[Googleの変更告知](https://android-developers.googleblog.com/2026/07/upcoming-changes-nearby-connections-api.html)

**本番はモバイルデータOFF、会場APから切断して自動再接続を止め、近距離用のWi-Fi無線とBluetoothはONとする。** 利用者の追加指示「wifi offに必ずしもする必要はありません」に基づく確定事項。Wi-Fi無線の完全OFFは必須試験・成立条件から外す。インターネット上流なしの専用APの追加は採用しない。

Xiaomi／vivoの1.5.22実機試験では、XiaomiのWi-Fi無線がON・AP未接続・ネット接続なしの状態で自動接続し、そこで保存したプロフィール更新をvivoでも一致確認した。これは近距離経路の実証であり、会場の全機種・20台の無線や安否／通報を含む全シーンの実証ではない。

アプリの「通信を使わない」スイッチだけをオフラインの証明にしない。Androidのネット検証状態、共有APIへの到達可否、端末間で作った更新IDの受信・保存を組み合わせて実演する。単一サーバーへの失敗だけでもインターネット全体の断絶を証明しない。OS設定の変更は参加者が行う。

### 2.2 PWAの自動復帰

現在の`lab/web/cloud-ui.mjs`には`online`／`visibilitychange`と前面時15秒周期の同期がある。ネット復帰イベントだけで成功扱いせず、実API成功・保存ACKまで再試行する。接続が回復しても`online`イベントが来ない場合は周期再試行で補う。[onlineイベントの意味](https://developer.mozilla.org/en-US/docs/Web/API/Window/online_event)

デモの成立条件は「PWAを前面で開いている、または通信設定からPWAへ戻った後、共有ボタン操作なしで同期」。閉じたPWA・ロック中の無操作復帰は保証対象にしない。Service Workerは常駐プロセスではなく、ブラウザーに停止され得る。Periodic Background SyncはWebKitが実装しない旨を表明している。[Service Workerの生存期間](https://web.dev/learn/pwa/service-workers)、[WebKitのPeriodic Background Sync方針](https://bugs.webkit.org/show_bug.cgi?id=204117)

iPhoneもインターネット接続を切ることが目的であり、Wi-Fi無線の完全OFFを必須にしない。モバイル通信とインターネットにつながるAPへの接続を止める。コントロールセンターのAP切断と無線の完全停止は異なる。[Appleの説明](https://support.apple.com/ja-jp/102412)

### 2.3 人数と復帰経路

- Android0台：聴衆のPWAはオフライン保存→オンライン復帰を体験できる。聴衆間のオフライン交換は成立しない。
- Android1台：その端末だけでは端末間交換にならない。運営のAndroidを相手にする必要がある。
- Android2〜20台：近距離接続とstore and forwardを体験できる。運営側に対応Android2台を用意できれば、聴衆の端末構成に依存せず実演できるが、当日の調達は未確定。
- PWAだけネットへ戻っても、Android群にしか存在しない未送信情報は取得できない。情報がサーバーへ届く経路が必要。
- 初回計画時は新規記録の投稿を元作成端末に限定していたが、続く指示で**署名付き原本のクラウド中継を実装した**。更新版Androidで本人の鍵をオンライン登録した後に作られ、Bへ保存された記録は、Aが不在でもBからサーバーへ送れる。エミュレーターのA→B→公開サーバー→独立PWA Cで元作成者の安否・通報の保存と表示を確認。実無線の追加試験とは区別する。[実装・試験記録](2026-10-31-offline-cloud-bridge.md)

## 3. 現在の実装との差分

- 1.5.22のNearby自動接続、最大4直接接続、保存・中継、切断復帰は土台として使える。実機2台、20個の共有処理、SQLiteを再度開いてからの中継は試験済み。
- 既存の多人数試験の中心はプロフィール記録。今回重要な**開始済みの地震、名簿、安否回答、通報・訂正**を含む40人シーンの一貫試験は別に追加する。
- 現在の参加APIは同一接続元で毎分30回の作成・参加制限がある。同じ会場Wi-Fiの40人＋再試行に対応する変更が必要。
- 現在のAndroid/PWA参加は招待コード方式。PWAでは参加後に住居登録を促すため、指定されたシーンへそのまま進めない。
- 管理者1人の訓練開始はある。会場デモ用の開始をこれに接続し、実際の緊急地震速報や本番の地震成立として配信しない。画面の題材は「地震」のまま、実施回の種別を会場デモとして区別する。
- 実際の端末位置と住居位置は既に区別されている。会場デモで住居の緯度経度を偽の現在地として流用しない。
- 安否表示には既存の匿名化・無事の表示条件がある。会場デモでは名前で相互確認する目的に合わせてデモ参加者名・無事／SOSを表示し、本番の表示規則を全体的に緩めない。
- 現APKは243,426,645 bytes（約243 MB）。Android20台が取得すると約4.87 GBになる。会場Wi-Fiの帯域とインストール所要時間を実測し、必要なら配布パッケージを軽量化または開始前に取得してもらう。既存の京都全域データを無断で削って対処しない。

## 4. データと参加の設計案

以下は実装用の提案であり、現行APIの実在を意味しない。

- `VenueSession {version, groupId, sessionId, incidentId, mode:"VENUE_DEMO", areaId, areaVersion}`：管理者が作成する実施回。一般参加者は変更不可。実施回を終えても通常グループ・実位置を消さない。
- `DemoPlacement {version, groupId, sessionId, memberId, latitude, longitude, slotId, source:"DEMO_ASSIGNED"}`：サーバーが参加時に一度割り当てる座標。再送・再起動・端末間同期で同じ値。全員同一の地域データ版を使う。
- 配置は事前に確認した地域内の陸上候補点から重複しないよう抽選する。40人が見やすい縮尺で分散し、水上・対象外・同一点へ割り当てない。配置範囲の正確な座標と候補点は地図上で確認してから確定する。
- 実際の住居・GPS用のテーブルを上書きせず、デモ座標を別テーブル／ストアに保存する。描画は実施回のmodeから位置ソースを選ぶ。会場デモ中の実GPS取得・既存の位置共有処理がデモ座標を上書き／漏送信しないよう入口でも分離する。
- `POST /api/v1/demo/join`（案）：`{groupName, password, requestId, deviceId, activityName}`を受け、メンバー資格情報とbootstrapを返す。画面上は「グループ名・パスワード→名前」の2段階でよい。名前確定時に一度だけ加入を確定し、二重タップ・応答消失後の再送を同一requestIdで重複なく処理する。
- bootstrapには実施回、最新名簿と必要な履歴、開始イベント、デモ座標、取得位置cursorを含める。記録が複数ページに分かれる場合も、準備完了まで取得する。Nearby接続鍵は既存の認証付きAPIからAndroidだけが取得する。
- 名前で参加先を特定するので、会場用の名前は有効期間中に一意とする。内部ID・履歴は従来どおり保持。表示名が同じ参加者は別メンバーIDで区別する。
- 参加パスワードはサーバー側で検証用ハッシュとして保持し、URL、QR、ログ、ソースへ平文を埋め込まない。既存のメンバートークンやNearby鍵とは別物にする。参加者に管理者権限を与えない。
- 成功した会場参加とパスワード誤入力を区別した制限・再試行を設け、40人の正当な同時参加を止めない。制限自体を全面撤去する方式は採用しない。
- 入室後の初回同期完了時に、名前とデモ位置だけで回答できる参加者情報を生成する。住所・寝室・架空の住居情報を捏造して入力要件を満たす方式にはしない。
- 地震／避難訓練では実GPSの取得値・時刻・精度を使う。権限未許可や取得不能時は取得状態を示し、京都の架空位置へ戻さない。iOSのバックグラウンド位置追跡をネイティブ同等に保証する計画ではない。
