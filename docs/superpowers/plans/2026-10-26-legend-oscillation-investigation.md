# 凡例の自動上下動：画面を操作しない調査

利用者から凡例操作後の画面振動を報告。vivo V2417Aの画面操作・再起動・更新・アプリ再起動は行わず、スクリーンショット6枚、logcat、window、gfxinfo、meminfoのみ取得した。診断データは `.implementation/screen-shake/` に保存。ソースコード変更は行っていない。

## 確認できた現象

- 2026-10-26 06:46 JST頃、凡例を表示したまま連続撮影。見出しの相対Y位置は0、65、78、0、21、53pxと往復した。ドラッグ用の取っ手・全壊率の行・下部ボタンもほぼ同量移動（下部は最大81px）。スクロールする本文だけではなくパネル全体の移動と微小な拡縮が見られる。
- システムの時計等は同位置。ウィンドウは1260×2800、Surface位置は(0,0)。凡例は独立したダイアログウィンドウとして表示されている。
- 約109秒を隔てたgfxinfoの累積描画回数は11,820→25,018と増加し、継続描画が発生している。複数ウィンドウの累積値なので表示FPSとは換算しない。
- 取得範囲のアプリログには、この現象に対応するクラッシュやメモリ不足のエラーは見つからない。これだけで他の問題を完全に否定するものではない。

## 原因の絞り込み

`SituationScreen.kt:125` の `ModalBottomSheet` は `skipPartiallyExpanded=true`、上端・下端の余白は標準設定。凡例の `Column`（145行付近）は `verticalScroll` を持つが高さの上限指定がない。説明文とボタンが追加され、実機ではほぼ画面全体の高さを使っている。他の建物詳細・住民一覧は高さを画面の一定割合に制限している。

実際に使用されているMaterial3は1.4.0。Gradleキャッシュの同バージョンのソースを読み、次の依存関係を確認した。

1. `SheetDefaults.kt` の標準余白は `safeDrawing` の上下を使用。
2. `ModalBottomSheet.kt:338` は現在のパネルY位置を上端余白の消費量に使い、362行で残った余白を内容に適用する。
3. 同295〜307行は測定後のパネル高さから展開時の停止位置を再計算する。
4. `AnchoredDraggable.kt` は測定時の停止位置更新を現在位置または進行中アニメーションに反映する。Material3には上方への行き過ぎ時にパネルを伸ばす処理もある。

**有力な原因は、画面いっぱいに伸びる凡例での「上下位置→余白→測定高さ→停止位置」のフィードバックと跳ね返りの相互作用。** 操作なしでパネル全体が往復する観測と一致する。地図タイルの読み込みによる単なるコマ落ちより、このレイアウト／アニメーションの問題を優先して調査する。

ただし現在位置・測定高さ・停止位置を内部計測したわけではなく、修正前後の再現比較も未実施。根本原因の最終確定と修正済みの主張はしない。公開issueはログイン要求で本文を確認できなかったため「公式に確認済みの同一不具合」とは扱わない。

## 修正時に行うこと

- 凡例の高さを安定した上限内に収め、上端余白と停止位置の循環を避ける最小変更から検証する。
- エミュレーターで、凡例を開く→上端へ速くスクロール→指を離す→複数秒放置という試験を追加。見出しとパネル位置が静止することを確認する。
- 実機の現在の状態を維持する指示があるため、今回の解析中は更新・操作を行わない。実機での修正確認は別段階。
- 前回の凡例開閉中心の試験では、スクロール後の放置で持続的な揺れが出ないかの確認が不足していた。

## 修正と再現試験（続報）

利用者から修正と他画面への再発防止を指示されたため実装。通常の `Column` スクロールと、住民一覧で使う `LazyColumn` を対象に回帰テストを追加する。

- 修正前のMaterial3を使ったエミュレーター試験で、内容高さを画面高に近づけ、取っ手を上へ80msでフリック。指を離して仮想時間2秒経過後にも、停止位置が **106.81564px** 動き続け、静止条件1.1px未満のテストが失敗した（`gap=140`）。全画面を超える長さだけの試験では再現せず、高さの条件に依存することも確認した。
- 共通の `PlanModalBottomSheet` を導入。上端の安全余白を動くパネルの外側に確保し、内部の余白処理は下端・左右のみとする。これにより上端余白がパネルの上下位置に連動して測定高さを変える循環を取り除く。下端・左右の安全領域と既存部品のキーボード回避は維持する。
- 本番コードの全2呼び出し箇所を共通部品に移行。対象は地図の凡例、住民一覧（全員・位置不明・重なった地点）、建物詳細、住民詳細、およびメイン側から開く住民詳細。
- その他のダイアログは `AlertDialog` であり、今回の位置依存のシート停止位置計算を使っていないため、同じ修正を広げない。
- 修正後のバージョンは1.5.11 / versionCode24。後続の試験結果は以下へ追記する。

## 回帰試験結果

- `SheetStabilityTest`：通常のスクロール列と住民一覧型のLazyColumn、それぞれ7段階の内容高さで確認。上方向へのフリック後、90フレームの位置変動は全条件で0px。2テスト成功（69.177秒）。修正前の106.81564pxに対して同じ判定条件で改善を確認した。
- vivoの凡例でもフリック後の連続6画像は、アプリ表示領域の画素差0。最初の3分放置試験は途中でユーザーによる設定画面への移動があったため、静止試験の成功として数えない。

## 別原因のフリーズと修正（1.5.12 / versionCode25）

シート修正後にも07:10:43 JSTのANRが記録された。アプリ自身の終了履歴からスタックを取得すると、画面の再生成中、ComposeがAndroidViewを取り外す際にMapLibreの`MapRenderer.nativeReset`で主スレッドが待機していた。これは06:54:51の旧ANRとは別の記録であり、旧記録の詳細まで同一原因だったとは断定しない。

Composeの`DisposableEffect.onDispose`にだけ地図の破棄を置くと、子SurfaceViewの切断処理が先行する。共通`PlanMapView`で親ビューの切断時に地図を破棄し、子SurfaceViewのレンダラー終了待ちより先に地図・ワーカーを終了する。破棄は二重実行を防ぎ、ライフサイクル通知も破棄済みなら処理しない。通常の状況地図と住民・位置選択用地図の双方へ適用した。

- 修正前：地図が破棄されないままSurface切断へ進むことを検出する回帰試験が失敗。
- 修正後：エミュレーターとvivo実機で、画面再生成を3回連続実行。各回の破棄順序、主スレッドの応答、再生成後の全壊率レイヤー再表示を確認し成功（20.657秒／24.345秒）。
- ビルドと建物関連JVMテストは成功。vivo実機にも1.5.12をインストール済み。更新画面の対象パッケージを確認して操作し、端末のセキュリティ設定・ロック設定は変更していない。

## 拡大すると色が消えるという報告の調査

- 京都の評価済み建物を中心に、ズーム12、13、13.9、14、14.1、14.5、15、15.5、16、16.8、18、20、22、および13.9→14.1→16.8への往復を実行。エミュレーターとvivoの両方で、全16段階において全壊率レイヤーの建物を検出した。ズーム20の実画像でも色付けを確認した。
- ソースタイルの最大ズーム16を超えた拡大にも対応しており、レイヤーの最大ズームは無制限。簡略形状と詳細形状を切り替える14付近にも欠落を再現できなかった。
- 一方、実機の通常画面では東京都の根津周辺を表示していた。京都データの外側にも同じ「建物の全壊率」という表示が残っていたため、表示領域が収録範囲と重ならない場合は「京都の収録範囲外」と表示するよう変更。ユーザーの現在地・登録住居は変更していない。
- これは観測できた範囲外表示への改善であり、報告された色消失の全ケースがこれで説明できるとは断定しない。拡大表示の回帰試験を残して継続検証できるようにした。
- 端末内の診断成果物は `.implementation/zoom-emulator/`、`.implementation/zoom-vivo/`、最終版の検証は `.implementation/final-vivo/` に保存。建物評価の数式・震度・分類閾値は変更していない。
